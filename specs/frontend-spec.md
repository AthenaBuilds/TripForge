# Frontend Spec — TripForge

## 1. Overview
<!-- Summary of the frontend application and its role. -->
A React single-page application (SPA) that lets a logged-in user create trips and build their itineraries item by item, with the ability to export a trip as PDF or Excel. It is a responsive web app (desktop + mobile) that talks to the TripForge backend over a REST API (see api-contract-spec.md).

## 2. Tech Stack
<!-- Framework, language, styling, state management, build tooling. -->
- Framework: React 18
- Language: TypeScript
- Styling: Tailwind CSS
- State management: TanStack Query (React Query) for server state; React Context for auth/session state; component-local `useState` for UI-only state
- Build tool: Vite
- Routing: React Router

## 3. Pages / Routes
<!-- List every route/page with its purpose. -->
| Route | Page | Description |
|-------|------|-------------|
| `/` | Welcome | Page 1 — landing page showing the "TripForge" name, tagline "From Ideas to Itinerary," and the login/signup forms (toggle between the two) |
| `/trips` | Trip Dashboard | Page 2 — entry point after login. Shows the user's existing trips, or an empty state ("No trips so far") if none exist. Above the "Add Trip" button, the user selects **Destination** and **From Date / To Date** for a new trip |
| `/trips/new/itinerary` | New Trip — Itinerary Builder | Page 3 — opened by "Add Trip" on page 2, carrying the destination/dates just entered. Lets the user add itinerary items one by one for the whole trip, then **Save Trip** (persists trip + items). **Export** is shown but disabled until the trip is saved (exports are generated by the backend) |
| `/trips/:tripId` | Trip Itinerary | View/edit an existing trip's itinerary (same item-by-item builder as page 3, pre-filled); includes Export (PDF/Excel), Share, and Delete Trip |
| `/shared/:slug` | Shared Trip (public) | Read-only itinerary for trip participants. **No login required** and not wrapped in `ProtectedRoute`. Shows destination, dates, "Planned by <name>", and items grouped by day; Export (PDF/Excel) is available; no edit controls. An unknown or revoked link shows "This trip link is no longer available." |

## 4. Components
<!-- Key reusable components and their responsibilities. -->
- `WelcomePanel` — displays the "TripForge" name and tagline "From Ideas to Itinerary" on page 1.
- `AuthForm` — shared form for login/signup (fields, validation, submit, toggle between modes).
- `NavBar` — top navigation, shows logged-in user, logout action.
- `ProtectedRoute` — route wrapper that redirects to `/` if no authenticated session.
- `TripList` / `TripCard` — renders the dashboard's trips in two sections, computed client-side using the user's local date:
  - **Upcoming**: trips with `endDate >= today` (including ongoing trips), soonest first. This is the API order.
  - **Past**: trips with `endDate < today`, most recent first (reversed).
  - An empty section is hidden. `TripCard` shows the destination, the date range, a relative hint ("in 78 days" or "Ongoing"), the item count, and a "Shared" badge.
- `NewTripDetailsForm` — captures Destination + From Date/To Date on page 2, before "Add Trip" is clicked. The Destination is the trip's overall label (placeholder: "e.g. Goa or South India").
- `ItineraryItemForm` — add one itinerary item at a time (activity, date/time, city, location, notes) on the itinerary builder. The optional **City** field is pre-filled with the city of the most recently added item, so single-city trips need no extra typing. It suggests cities already used in this trip (`<datalist>`).
- `ItineraryItemList` / `ItineraryItemCard` — read-only display of added itinerary items, grouped by day, with edit/remove actions. A card shows a small city badge when `city` is set. A day header lists the distinct cities for that day (e.g. "Dec 22 · Bengaluru → Mysuru").
- `ExportButton` — triggers export of a saved trip's itinerary as PDF or Excel. Disabled (with a "Save the trip to export" hint) when there is no `tripId` yet.
- `SaveTripButton` — persists the trip (destination, dates, itinerary items).
- `ShareTripPanel` — on `/trips/:tripId`. "Share" turns on link sharing and shows the link with a **Copy link** button (Clipboard API). It also offers **Stop sharing** (revokes the link, after a confirmation) and **New link** (revoke + share, after a confirmation).
- `SharedTripView` — read-only page for `/shared/:slug`. It reuses `ItineraryItemList` in a `readOnly` mode that hides edit/remove actions.
- `LoadingSpinner` — shared loading indicator for async states.
- `ErrorBanner` — shared inline error display for failed requests/form validation.
- `EmptyState` — shared "nothing here yet" placeholder (no trips, no itinerary items).

## 5. User Flows
<!-- Step-by-step flow through the UI for core use cases (link back to goal-spec use cases). -->
- **Signup/Login**: user lands on `/` (Welcome) → toggles to signup or login in `AuthForm` → submits credentials → on success, redirected to `/trips`.
- **View trips**: on `/trips`, see existing trips as `TripCard`s grouped into Upcoming and Past, or an `EmptyState` ("No trips so far") if none exist.
- **Start a new trip**: on `/trips`, fill `NewTripDetailsForm` (Destination, From Date, To Date) → click "Add Trip" → navigates to `/trips/new/itinerary`, carrying the destination/dates along.
- **Build itinerary (new trip)**: on `/trips/new/itinerary`, repeatedly fill `ItineraryItemForm` and add items one by one → each appears in `ItineraryItemList`.
- **Save new trip**: click "Save Trip" → persists the trip (destination, dates, all itinerary items) → redirected to `/trips/:tripId`.
- **Edit/remove itinerary item**: click edit/remove on an `ItineraryItemCard` (works the same on `/trips/new/itinerary` and `/trips/:tripId`) → update or confirm removal → list updates.
- **View/edit an existing trip**: from `/trips`, click a `TripCard` → `/trips/:tripId` → shows destination, dates, and all itinerary items; items can be added, edited, or removed.
- **Export**: from `/trips/:tripId`, click "Export" → choose PDF or Excel → the backend generates the file → it downloads. On `/trips/new/itinerary`, Export is disabled until "Save Trip" succeeds (which redirects to `/trips/:tripId`, where Export is enabled).
- **Share trip**: on `/trips/:tripId`, click "Share" → a link is created → click "Copy link" → send it to participants (WhatsApp, email, etc.). `TripCard` on the dashboard shows a "Shared" badge.
- **View shared trip (participant)**: open `/shared/:slug` → read-only itinerary, with no login → optionally Export PDF/Excel.
- **Revoke sharing**: on `/trips/:tripId`, click "Stop sharing" → confirm → the link stops working immediately.
- **Delete trip**: from `/trips/:tripId`, click "Delete Trip" → confirm → trip removed, redirected to `/trips`.

## 6. State Management
<!-- What state is local vs global. How data is fetched/cached (e.g. React Query, Redux). -->
- **Server state** (trips, itinerary items, current user) is fetched and cached via TanStack Query; mutations (create/edit/delete) invalidate the relevant query keys to keep views in sync.
- **Auth/session state** (current user, auth token presence) lives in a React Context, set on login/signup and cleared on logout.
- **New-trip draft state** (destination, from date, to date entered on `/trips`, and itinerary items added on `/trips/new/itinerary`) is held in a `DraftTripContext` and auto-saved to `localStorage` (debounced, ~500 ms) until "Save Trip" persists it in one go. Nothing is written to the backend before that point.
  - Key: `tripforge:draft:<userId>`, so drafts are kept separate per user on shared devices. Value: `{ version: 1, destination, startDate, endDate, items, updatedAt }`.
  - Only **one draft** per user at a time. Starting a new trip while a draft exists asks "Resume draft or start over?".
  - On `/trips`, if a draft exists, a "Resume draft: <destination>" banner offers **Resume** (→ `/trips/new/itinerary`) and **Discard**.
  - The draft is cleared on a successful Save Trip, on Discard, and on logout.
  - Reloading `/trips/new/itinerary` restores the draft from `localStorage`. With no draft, the page redirects to `/trips`.
  - All `localStorage` access is wrapped in try/catch. If storage is unavailable (e.g. private mode), drafts only live in memory and the app still works.
  - Drafts that don't parse or have an unknown `version` are discarded.
- **UI-only state** (form inputs before submit, modal open/closed) stays local to the component via `useState`.

## 7. API Integration
<!-- Which endpoints each page/component calls (link to api-contract-spec.md). -->
Exact request/response shapes are defined in api-contract-spec.md. All calls go to the relative base path `/api` (proxied to the AWS backend by Vercel in production and by Vite in local dev), with `credentials: 'include'`. Paths below are shown without the `/api` prefix. At a high level:
- Welcome page calls `POST /auth/signup` and `POST /auth/login`.
- Trip Dashboard calls `GET /trips`.
- "Save Trip" (on `/trips/new/itinerary`) calls `POST /trips` with destination, dates, and the full list of itinerary items.
- Trip Itinerary page (`/trips/:tripId`) calls `GET /trips/:tripId` and the itinerary-item endpoints (`POST` / `PATCH` / `DELETE /trips/:tripId/items/:itemId`) for incremental edits, plus `DELETE /trips/:tripId` for Delete Trip.
- Export calls `GET /trips/:tripId/export?format=pdf|xlsx` and downloads the returned file.
- `ShareTripPanel` calls `POST /trips/:tripId/share` and `DELETE /trips/:tripId/share`, then invalidates the trip query.
- `SharedTripView` calls `GET /shared/:slug` and `GET /shared/:slug/export?format=…` without relying on a session. A 401 is never expected here, and the global 401 → redirect handler must not run on `/shared/*` routes.

## 8. UI/UX Requirements
<!-- Design system, responsiveness, accessibility, theming. -->
- Mobile-first responsive layout using Tailwind breakpoints; must be fully usable on a phone-sized viewport as well as desktop.
- Simple, clean visual style — no custom design system beyond Tailwind's defaults for this version.
- Typography: **Montserrat** for headings, **Open Sans** for body text (loaded via Google Fonts, configured as Tailwind `fontFamily` tokens — e.g. `font-heading` / `font-body`).
- Forms use proper `<label>` elements and visible focus states; interactive elements are keyboard-navigable.
- No dark mode requirement for MVP (can be a stretch item).

## 9. Error & Loading States
<!-- How errors, empty states, and loading states are handled. -->
- `LoadingSpinner` shown while a query/mutation is in flight (including while an export file is being generated).
- `ErrorBanner` shown for failed API calls (network error, 4xx/5xx) with a human-readable message.
- Inline field-level validation errors on forms (e.g. missing required field) shown before submit where possible.
- `EmptyState` shown when a user has no trips yet ("No trips so far"), with a call-to-action to add one.

## 10. Authentication & Authorization (Frontend)
<!-- Login/signup flows, protected routes, token storage. -->
- Basic auth is required for the MVP — all `/trips*` routes are wrapped in `ProtectedRoute` and require a logged-in session. `/shared/:slug` is public.
- Login/signup both live on the `/` Welcome page via `AuthForm` (toggle between modes) — there are no separate `/login`/`/signup` routes.
- The session is a JWT in an **httpOnly cookie** set by the backend (see backend-spec.md §7). The frontend never reads or stores the token; it calls `GET /auth/me` on app load to restore the session into the auth Context.
- On 401 responses, the frontend clears the session and redirects to `/`.
- Logout clears session state and redirects to `/`.

## 11. Performance Requirements
<!-- Load time targets, lazy loading, code splitting. -->
- No strict performance budget for this learning/portfolio project; reasonable defaults only.
- Route-level code splitting via `React.lazy` for page components.
- Avoid unnecessary re-renders (memoize list items where it matters); no premature optimization beyond that.

## 12. Testing Strategy
<!-- Unit, integration, e2e tooling and coverage expectations. -->
- Unit/component tests with Vitest + React Testing Library, focused on core components (`NewTripDetailsForm`, `ItineraryItemForm`, `ProtectedRoute`) and critical flows (add trip details, add itinerary item, save trip).
- No end-to-end test suite for MVP; can be added later (e.g. Playwright) as a stretch item.
- No formal coverage target — tests should cover the core use cases from goal-spec.md.

## 13. Deployment
- Hosted on **Vercel**: it builds the Vite app (`npm run build` → `dist/`) from the `/client` directory, with preview deployments for pull requests and production deploys from `main`.
- `vercel.json` defines:
  - a rewrite from `/api/:path*` to the AWS backend (the API Gateway default URL, `https://<api-id>.execute-api.<region>.amazonaws.com/:path*`), so API calls and the auth cookie stay same-origin;
  - an SPA fallback rewrite from all other paths to `/index.html`, so React Router deep links (e.g. `/trips/123`) work on refresh.
- No secrets live in the frontend. The backend URL is only in `vercel.json`, not in client code.
- Preview deployments use different `*.vercel.app` origins. They still work because API calls go through each preview's own `/api` rewrite. Note: previews call the **production** backend, since there is no staging environment, so previews use real data.

## 14. CI
- The `client` job in `.github/workflows/ci.yml` runs when `client/**` or `shared/**` changes: install → ESLint → `tsc --noEmit` → Vitest + React Testing Library → `vite build`. Full pipeline definition: backend-spec.md §15.
- Vercel is the frontend CD:
  - The Vercel project's **Root Directory** is `client`.
  - An **Ignored Build Step** (`git diff --quiet HEAD^ HEAD -- . ../shared`) skips builds when nothing in the frontend or `/shared` changed.
  - Production deploys from `main` wait for the GitHub `ci-ok` check before they are promoted.
- Because the backend may deploy before or after the frontend, the frontend must tolerate extra, unknown fields in API responses. It relies only on fields defined in api-contract-spec.md.
